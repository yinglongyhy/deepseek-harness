# 同步上游

将官方更新整合到自定义分支，保持官方历史不变、自定义提交按功能组织。仅在用户显式调用时执行。

读取[自定义维护清单](../../../CUSTOMIZATIONS.md)，获取已验证基线、自定义功能依赖、退出条件和已知限制。按受影响功能读取实现与说明，不一次性加载所有引用。遵循[项目 Git 规则](../../../AGENTS.md#git-提交)；暂存、提交、推送自定义分支和部署不包含在本流程的授权中。

## 1. 建立恢复点

确认工作区干净、没有未完成的 Git 操作，且 `refs/customizations/upstream-base` 存在。任一条件不满足时停止，不自动 stash、丢弃修改或用远端分支代替已验证基线。新克隆缺少基线引用时，先确认并恢复其精确提交。

记录当前自定义分支和基线的精确提交，建立不会随 rebase 改写的恢复引用；确认恢复点可解析后才修改分支，不依赖 reflog 保留时长。

## 2. 获取官方更新

不通过 pull 为 `develop` 整合官方更新。核对 Fork 的官方来源及 `origin` 地址，通过 GitHub Sync fork 更新远端 Fork 的 `master`，再 fetch `origin`，将本地 `master` 快进到 `origin/master`。遇到分叉、冲突或无法快进时停止调查，不强制覆盖远端或本地提交。

## 3. 评估影响

比较已验证基线与更新后的本地 `master`，按维护清单检查实际调用、依赖和行为变化，不以文件重叠或 Git 冲突判断影响。

- 不涉及自定义及其依赖：无需逐项确认功能方案，但仍须确认是否执行 rebase。
- 涉及相关接口、逻辑、行为或同类功能：整理影响、推荐方案及取舍，纳入执行前预览，由用户确认。
- 后续发现新的相关影响：补充确认，不沿用旧确认扩大调整范围。

## 4. 执行前预览与确认

本地 `master` 更新且影响评估完成后，先展示以下预览，再询问是否执行，不提前 rebase 或修改自定义实现。

### 上游新增内容

标明已验证基线、目标 `master` 和当前 `develop` 的精确提交。汇总基线到目标之间的新增功能、修复、行为与接口变化及破坏性变更；按主题组织并附可追溯的提交或 PR，不只列出与自定义功能相关的更新。

### 自定义提交影响表

从实际 Git 历史识别本次待重放的全部自定义提交，按重放顺序逐条列出，不仅列出预计有冲突的提交，也不用维护清单的功能条目代替提交清单。每行使用以下字段：

| 自定义提交 | 功能／目的 | 与上游新增内容有交叉 | 影响点 | 建议 |
|---|---|---|---|---|
| 提交标识与标题 | 该提交保留的能力 | 是／否／待核实；关联上游变更 | 涉及的接口、依赖或行为及具体风险 | 保留／适配／复用上游／移除／暂缓，并说明理由 |

交叉判断依据实际调用、依赖、行为或同类功能，不把文件重叠等同于冲突，也不把无文本冲突等同于无影响。无法确定的项标为“待核实”，说明缺少的证据，不写成“无影响”。复用或移除的建议需说明上游是否覆盖原有能力及限制。

### 执行确认

按[验证参考](references/validation.md)选择受影响检查，总结拟执行的 rebase、建议采用的调整、验证范围和待决事项，明确询问用户是否按此预览执行。无论是否存在交叉，都必须等待用户明确同意；调用本 skill 或此前确认功能方案不代替本次执行确认。

未获同意时停在此处，不改写 `develop`，不推进已验证基线。确认后若目标提交或影响范围变化，重新确认。

## 5. Rebase 自定义提交

切回 `develop`，将自定义提交 rebase 到本地 `master`，保持功能分组和依赖顺序。不改写官方提交，不用 merge 将 `master` 合入 `develop`；解决冲突不自动授权改变功能。

命令失败或状态不确定时停止依赖步骤，先调查再继续，不自动重试破坏性操作。

## 6. 验证并更新基线

对照 rebase 前后的功能差异，检查遗漏、重复和误引入。按[验证参考](references/validation.md)执行已确认的受影响验证，不把历史通过记录或 rebase 成功当作验收，不自动刷新快照预期输出。

相关验证通过后，才将 `refs/customizations/upstream-base` 推进到本次整合的官方提交，并更新维护清单的发布基线、接口依赖、退出条件和已知限制；验证结果在本次完成报告中记录，不向事实清单追加执行流水。验证失败或未完成时保留旧引用，即使远端和本地 `master` 已更新。

## 完成报告

简要报告：

- 同步前后基线、自定义分支和恢复引用。
- 自定义功能的保留、调整或移除结果，以及需要用户处理的问题。
- 实际执行的验证，分别列明通过、失败和未执行项。
- 基线是否推进，以及剩余风险。

GitHub Sync fork 不授权推送自定义分支。推送需单独明确授权及目标，首次授权推送时再建立远端跟踪；改写远端历史仅使用带精确远端旧值的 `--force-with-lease`，远端变化就停止，不使用 `--force`。GUI 部署、重启和真实服务／Desktop 手工验收单独处理，不从代码验证结果推导完成。
